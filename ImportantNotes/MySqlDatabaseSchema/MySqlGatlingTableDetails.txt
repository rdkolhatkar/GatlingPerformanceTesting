============================================================
1. CREATE DATABASE / SCHEMA
============================================================

-- Create the database/schema if it does not already exist.

CREATE SCHEMA IF NOT EXISTS gatlingdatabasefeeder;


-- Select the database.

USE gatlingdatabasefeeder;


============================================================
2. CREATE TABLE
============================================================

-- Create the table used by the Gatling MySQL feeder project.
--
-- user_id:
--   BIGINT + AUTO_INCREMENT means MySQL generates the ID.
--
-- user_name:
--   Required and must be unique.
--
-- email:
--   User email address.
--
-- first_name / last_name:
--   User name fields.
--
-- mobile:
--   10-digit mobile number.
--
-- password:
--   Practice password field.

CREATE TABLE IF NOT EXISTS userDataFeeder (
    user_id BIGINT NOT NULL AUTO_INCREMENT,
    user_name VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    first_name VARCHAR(255) NOT NULL,
    last_name VARCHAR(255) NOT NULL,
    mobile VARCHAR(10) NOT NULL,
    password VARCHAR(255) NOT NULL,
    PRIMARY KEY (user_id),
    UNIQUE KEY uk_user_name (user_name)
);


============================================================

IMPORTANT:
Always use a WHERE clause when you intend to update
specific records.

Without WHERE:

UPDATE userDataFeeder
SET first_name = 'Test';

This would update EVERY record in the table.

============================================================
23. TRUNCATE TABLE
============================================================

-- Remove all records quickly.

TRUNCATE TABLE userDataFeeder;


IMPORTANT:
TRUNCATE removes all records and resets the AUTO_INCREMENT
counter in MySQL.

This is useful for resetting the database before repeating
the Gatling CSV-to-DB loading exercise.


============================================================
24. DROP TABLE
============================================================

-- Completely remove the table.

DROP TABLE userDataFeeder;


-- Safer version:

DROP TABLE IF EXISTS userDataFeeder;


IMPORTANT:
DROP TABLE removes:
    1. The table
    2. All records
    3. The table structure

28. FIND DUPLICATE USERNAME
============================================================

SELECT
    user_name,
    COUNT(*) AS occurrence_count
FROM userDataFeeder
GROUP BY user_name
HAVING COUNT(*) > 1;


NOTE:
The table has a UNIQUE constraint on user_name, so duplicate
usernames should normally be rejected by MySQL.

36. IMPORTANT DIFFERENCE: DELETE vs TRUNCATE vs DROP
============================================================

DELETE
------

DELETE FROM userDataFeeder;

Purpose:
    Removes rows.

Table:
    Remains.

AUTO_INCREMENT:
    Normally continues from its current counter.

Can use WHERE:
    Yes.


TRUNCATE
--------

TRUNCATE TABLE userDataFeeder;

Purpose:
    Removes all rows quickly.

Table:
    Remains.

AUTO_INCREMENT:
    Resets in MySQL.

Can use WHERE:
    No.


DROP
----

DROP TABLE userDataFeeder;

Purpose:
    Removes the entire table.

Table:
    Removed.

Data:
    Removed.

Structure:
    Removed.

Can use WHERE:
    No.

37. IMPORTANT NOTE FOR THIS GATLING PROJECT
============================================================

The project uses:

user_id BIGINT AUTO_INCREMENT

The sample users.csv does NOT contain user_id.

This is intentional.

When CSV records are inserted:

CSV
 |
 +-- user_name
 +-- email
 +-- first_name
 +-- last_name
 +-- mobile
 +-- password
 |
 v
MySQL INSERT
 |
 v
MySQL generates user_id automatically.


For the sample data, the first inserted record gets:

user_id = 1

The second:

user_id = 2

and so on.


============================================================
38. JSONPLACEHOLDER CONNECTION
============================================================

The Gatling simulation uses:

https://jsonplaceholder.typicode.com

The example request is:

GET /posts/${user_id}


For example:

user_id = 1
    |
    v
GET /posts/1


user_id = 2
    |
    v
GET /posts/2


JSONPlaceholder provides post IDs 1-100, so the sample
database starts with IDs that work with this endpoint.


============================================================
39. SECURITY NOTE
============================================================

The password column in this practice table contains
plain-text practice values.

DO NOT use this approach for a real production application.

Real applications should:
    - Hash passwords.
    - Never store plain-text passwords.
    - Never expose passwords in Gatling logs.
    - Never commit database credentials to Git.
    - Use environment variables or a secret manager.
